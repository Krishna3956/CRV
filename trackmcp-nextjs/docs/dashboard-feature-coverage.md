# Dashboard feature-to-product coverage matrix

Status: implementation-branch contract for the business-first dashboard.

This document maps repository capabilities to the questions a business user needs answered. It is a product boundary, not a catalog of every telemetry field. A capability is included in the primary dashboard only when the current API can support an honest, bounded, privacy-safe interpretation.

## Scope and source inventory

Reviewed on the implementation branch:

- `PRD-P1-03-tool-quality-analytics.md` — bounded Tool Quality, catalog reconstruction, explicit workflow outcomes, minimum volumes, live/sample separation, and insufficient-data semantics.
- `src/lib/telemetry/analytics-types.ts`, `analytics.ts`, `types.ts`, and `tool-quality.ts` — analytics, trace, provenance, workflow, catalog, intent, and Tool Quality contracts.
- `src/lib/telemetry/regressions.ts` and `src/lib/alerts/types.ts` — regression metric definitions, data-status reasons, incident lifecycle, severity, evidence, and delivery state.
- `scripts/p0-04-truth.test.mjs` — truthfulness, live/sample, completion-source, bounded-trace, privacy, and setup expectations.
- `scripts/p1-02-intent-capability.test.mjs` — intent and missing-capability storage constraints.
- `docs/p1-05-alerts-migration-apply.md` and alert lifecycle/migration tests — P1-05 persistence and operational boundaries.
- Dashboard implementation and contract tests in `src/components/dashboard/` — current navigation, state boundaries, KPI ordering, trace behavior, and route/query rules.
- Analytics, Tool Quality, validation, regression, observation-source, API integration, SDK, and Python test locations listed in the test map below.

The repository contains a standalone P1-03 PRD. No standalone tracked P0-04, P1-02, P1-04, or P1-05 product PRD was found in this checkout; for those areas, the implementation contracts, tests, types, and operational documentation are the source evidence. Any behavior not supported by those contracts is marked as an API/product gap rather than represented by invented UI data.

## Primary-dashboard inclusion rules

1. The primary experience answers usage, completed work, quality, and what needs attention. It does not mirror the telemetry schema.
2. A KPI must identify its data source, time range, denominator/eligible volume where relevant, and evidence status. If the API cannot support the claim, the UI uses a neutral or insufficient-data state and links to the gap.
3. Explicit workflow outcomes are the only source for Work completed. Sessions, traces, tool calls, successful responses, and session heuristics cannot substitute for an outcome event.
4. Analytics and Tool Quality calculations use server observations only. Client observations are diagnostic/provenance evidence.
5. Example data is opt-in (`data=example`); My data is explicit (`data=my`). No empty or failed live response may silently become Example data.
6. Technical infrastructure — trace IDs, correlation handles, protocol payloads, raw catalog schemas, delivery payloads, and SDK internals — is progressively disclosed under Evidence or Setup.
7. All pages preserve bounded, redacted, truncated, unavailable, permission, empty, insufficient, loading, and error states. A missing value is never silently converted to zero or “healthy.”
8. No freshness, active-state, reachability, installation, identity, customer, causal, or health claim is made without a supporting API contract.

## Explicit API/product gaps

- **P1-05 dashboard integration:** alert lifecycle and persistence contracts exist, but the redesigned dashboard does not currently query/render authenticated incidents. Issues must receive a workspace-scoped incident contract before active alerts are shown. Until then, no alert data is fabricated and no Alerts navigation item is added.
- **Insight confidence metadata:** the current analytics insight response does not consistently provide threshold, confidence, and eligible-volume metadata. The dashboard therefore uses neutral wording and says when evidence metadata is not provided; it does not rank an insufficient result as a confirmed issue.
- **Freshness and stale status:** the APIs do not provide a last-observed timestamp or stale-state signal. The dashboard does not show “updated just now,” “connected to live telemetry,” or equivalent claims.
- **Custom ranges:** the current bounded API contract supports the 7/30/90-day presets. A calendar-based Custom range remains unavailable until the API supports bounded custom scans and query-state validation.
- **Setup verification:** current APIs support key/setup actions and first-event guidance, but do not prove SDK installation, server reachability, or delivery after a check. Setup copy remains instructional and honest.
- **Identity and reach:** AI clients observed are not users or customers. No user/customer adoption, unique-person reach, or product-health claim is derived from client names or sessions.
- **Standalone PRD coverage:** no standalone tracked P0-04, P1-02, P1-04, or P1-05 PRD was found in this checkout. Those areas remain bounded by their implementation types, tests, and operational docs until product-level PRDs are added.

## Decision record

If a future backend capability cannot be mapped to a customer question, a business-readable summary, a bounded evidence path, and explicit state semantics, it must remain out of the primary dashboard. The implementation should record the capability as an API/product gap and wait for a contract instead of manufacturing a metric or promoting an engineering diagnostic into a business claim.
