# TrackMCP dashboard data contract — 2026-11

This document records the backend source for every business-facing dashboard
surface. A dashboard metric is only considered implemented when its UI value
can be traced to the analytics response, the source projection, and a bounded
test or runtime check.

## Shared transport

- Browser entry point: `trackmcp-nextjs/src/components/dashboard/DashboardApp.tsx`.
- Live analytics request: `GET /api/v1/analytics` from the dashboard page.
- Server handler: `trackmcp-nextjs/src/app/api/v1/analytics/handlers.ts`.
- Response contract: `trackmcp-nextjs/src/lib/telemetry/analytics-types.ts` (`Analytics`).
- Bounded source: workspace-scoped `trackmcp_events` and the durable Founder OS
  projections when available. The handler preserves `data_trust` and does not
  turn unavailable evidence into zero.
- Example mode is generated by `exampleAnalytics()` and `exampleQuality()` in
  the dashboard component. It is explicitly separate from live workspace data.

## View mapping

| View | UI signals | Analytics fields / source | Truth boundary |
| --- | --- | --- | --- |
| Overview | assistants, observed work, reported completion, attention, period comparison, timeline, sessions | `clients`, `tool_calls`, `outcomes`, `insights`, `who_is_using_it`, `capability_activity.previous_period_calls`, `timeline`, `workflows`, `data_trust`, `founder_os` | Completion is explicit-outcome-only; missing events are not abandonment or failure. |
| Who's using it | active/new/returning account groups, weekly growth, assistant mix, top account groups | `who_is_using_it` | Account groups are privacy-safe resolver signals, not people or customer counts. |
| What they're doing | capability volume, adoption breadth, trend, reliability, tool detail | `capability_activity`, `tool_adoption`, `tools` | Tool names and counts are bounded; raw identity keys never reach the browser. |
| Resources & prompts | reads/calls, completion/stall/error rates, transport coverage, breakdowns | `resource_prompt_activity`, `interaction_surfaces` | Content and arguments are not exposed; unavailable rates remain `N/A`. |
| The journey | interaction count, typical length, stalled/resumed interactions, paths, drop-off | `journey_activity`, `workflows`, `outcomes` | Paths describe observed server interactions, not a customer's complete business task. |
| Did it work | explicit completion/failure/unknown states, task states, tool quality, latency | `outcome_activity`, `founder_os.facts`, `ToolQualityResponse` | Unknown and insufficient evidence remain distinct from failure. |
| What's broken | actionable signals, incidents, severity, affected volume, evidence, action queue | `issue_activity`, `insights`, alert incident APIs, action queue API | A signal is not a diagnosis; synthetic/canary evidence remains labeled. |
| Evidence | bounded sessions, event timeline, incident evidence, delivery attempts | `workflows`, trace API, alert delivery API | Payloads are bounded/redacted and identifiers stay opaque. |
| Setup | workspace, keys, first event, server readiness, SDK/OTLP guides | workspace/key routes, first-event checks, setup/readiness APIs | Setup is operational state, not analytics; no key is shown after creation. |

## Verification rule

When adding a metric:

1. Add or reuse a typed field in `Analytics` or the relevant response type.
2. Implement the bounded server calculation in the analytics handler or an
   existing projection.
3. Render `N/A`, an insufficient-data reason, or an empty state when the source
   cannot support the claim.
4. Add a contract test for the UI and a focused test for the calculation.
5. Include the source field and limitation in this document.

No new dashboard card should be backed only by hard-coded example values in live
mode.
